## 1. Policies with role `anon` or `public` (schemas `public` and `storage`)

This covers 164 policies, from `pg_policies where roles && '{anon,public}'`.

A `public` policy also applies to `anon`. Most `public` policies are safe for `anon` anyway, because they compare against `auth.uid()`, `current_org_id()` or `get_user_org_id()`, and all of those are NULL for anon. The only exception is the `auth.role() = 'authenticated'` form: it is false for anon, but it gives no organisation scoping for signed-in users.

### A. Anonymous writes

| A2 | `quotes` | `Public portal update` | UPDATE TO anon USING/CHECK (quote_token IS NOT NULL) | **All 9 quotes** have a token. Anonymous users can update any column on any of them: prices, status, org. | Not dropped: BUILT customer portal, needs your call |

**What B1–B3 have in common.** Each checks only that a token *exists*, not that it *matches* what the caller holds. The safe pattern is a SECURITY DEFINER RPC that takes the token, such as the existing `get_proof_by_token`, with no anon table policy. That work belongs in BUILT, not 007.

### C. Cross-organisation access for signed-in users (not anon)

`USING (auth.role() = 'authenticated')` gives no organisation scoping:

- **ALL:** `bom_template_items`, `bom_templates`, `change_orders`, `job_activities`, `job_payments`, `lead_activities`, `led_spacing_chart`, `quick_catches` (23 rows), `quote_tasks`, `sign_template_items`, `sign_templates`, `site_survey_presets`, and `patrol_sessions` (fixed by 007)
- **SELECT only:** `sign_main_categories` and `sign_sub_types`. These are probably shared reference data, so probably fine.
- **INSERT:** `artwork_review_events.authenticated_insert_events`. Any signed-in user can add events to any organisation's review.

### D. Privilege escalation found along the way (not anon; not in 007)

- **`users.org_isolation`** is `ALL TO public USING (organisation_id = get_user_org_id())` with no WITH CHECK. `authenticated` has column UPDATE on `users.role`, and `users` has no triggers. *Inferred:* any active user can set `role = 'admin'` on themselves or on anyone in their organisation. **High.** I did not test it; that would be a write.
- **`organisations.org_isolation`** is `ALL`, which permissive-ORs with `organisations_update_none`. *Inferred:* members can update their own organisation row.

### Checked and OK

- `catalog_items_resolved` is the only public view, and it is `security_invoker=true`, so base-table RLS applies.
- No `public` table has RLS disabled.

## 3. Migration 007 (written, not applied)

`migrations/007_patrol_sessions_org_rls.sql`:

- Drops `patrol_sessions."All authenticated users"`.
- Adds three policies, all TO authenticated, with the organisation derived through `patrol_routes.organisation_id = (SELECT get_user_org_id())`:
  - `patrol_sessions_select_org` (SELECT): any session on a route in my organisation.
  - `patrol_sessions_insert_own` (INSERT): `patroller_id = auth.uid()`, and the route is in my organisation.
  - `patrol_sessions_update_own_or_admin` (UPDATE): route in my organisation, and either my session or I'm an admin. The same test applies to the new row.
- **No DELETE policy.**
- Drops `patrol_businesses.anon_insert_businesses`.
- `CREATE INDEX IF NOT EXISTS idx_patrol_sessions_route_started ON patrol_sessions (route_id, started_at DESC)`. This is a no-op live, because the index is already there.

`migrations/007_rollback.sql` recreates both dropped policies exactly as captured from live `pg_policies` (PERMISSIVE, same roles, same USING/CHECK). It does **not** drop the index, since the index existed before 007.

**What I left out on purpose:**
- `route_id SET NOT NULL`. There are 0 NULLs live, and the policies already reject or hide a NULL route, so 007 stays policy-only.
- A2 and B1–B4. They serve BUILT and legacy photos, so they need your decision.
